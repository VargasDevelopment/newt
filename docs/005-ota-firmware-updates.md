# Decision 005: OTA firmware updates are a product requirement

The owner explicitly requested OTA on October 1, 2026. This is separate from installing tiny Newt apps: firmware changes the platform and boot path; app packages use trusted components and semantic actions inside that platform. Neither updater is physically implemented in this checkpoint.

Keep the current menu/settings slice bounded. The next updater slice should first inspect pinned official FreeInk recovery/update examples and the actual cracked unit's bootloader, partition layout, security/recovery capabilities and flash capacity during a separately authorized session. An OTA design cannot assume the PlatformIO sample table matches stock hardware, or that app-level RecoveryBoot rescues a broken startup. USB-locked units require a verified recovery route before experimental firmware.

The smallest useful next deliverable is a testable update state machine and fault harness, then a concrete compatible image/slot plan for this unit. Require a pinned release identity, device/ESP32-C3 and capacity compatibility, a bounded verified download with exact size and integrity check, adequate battery/power, clear progress/cancellation/error states, interrupted-write safety and an explicit recovery/rollback procedure. Preserve the running image and data; do not select an unverified image or silently rewrite partitions. Hash verification against trusted release metadata proves the expected bytes, not provenance by itself. Determine actual bootloader rollback/confirmation support before promising automatic rollback. A fresh working boot should pass a bounded health check before confirmation where supported.

Network credentials, distribution/authenticity policy, firmware hosting/publication and native install tests require concrete scope when reached. This record itself adds no updater. The current OTA design, its phased plan and the owner decisions it needs are in [082](082-ota-updates.md); the owner's Wi-Fi network is the one approved credential (owner approval 2026-10-27, AGENTS.md). A signing framework, partition change, hardware action or public release still needs its own owner approval. The owner's separate stock SD `update.bin` CrossInk installation task remains separate from Newt OTA.


## Requested update channels, October 1 follow-up

The owner explicitly requested eventual support for the same practical flashing mechanisms as CrossInk: **OTA firmware updates, SD-card firmware flashing and USB recovery**, so new builds can be transferred and tested rapidly. Treat first installation, Newt-owned updating and recovery as different operations. Preserve a verified recovery route while iterating; installing a Newt image without an updater does not inherit the previous firmware's app-level SD/OTA mechanisms. The next implementation scope should include a shared image validator, device/partition/power preflight, interruption/recovery tests and a small build→transfer→test workflow for each supported transport. This requirement authorizes design/source work, not a particular device or SD write. The current ROM identification/full-backup preflight remains read-only.
